# Jenkins Inbound (JNLP/WebSocket) Agent

This guide covers the Jenkins **Launch agent by connecting it to the controller** method, manual/background execution, systemd, secrets, and common troubleshooting.

> Jenkins now commonly uses the term **inbound agent**. Older UI/documentation may call it a **JNLP agent**. This guide uses WebSocket because that is the command generated by the current Jenkins UI.

## 1. SSH vs inbound agent

### SSH

The controller starts the connection:

```text
Jenkins Controller
       |
       | SSH
       v
   Agent VM
```

### Inbound / JNLP

The agent starts the connection:

```text
Jenkins Controller
       ^
       | WebSocket / HTTPS
       |
   Agent VM
```

This is useful when the agent can reach Jenkins but Jenkins cannot directly SSH to the agent.

---

## 2. Create the node

Go to:

**Manage Jenkins -> Nodes -> New Node**

Create a permanent node.

Example:

```text
Name: ubuntu-agent-01-JNLP
Number of executors: 1
Remote root directory: /home/rohit/agent
Labels: ubuntu-agent-jnlp
Usage: Use this node as much as possible
Launch method: Launch agent by connecting it to the controller
```

After saving, Jenkins displays a generated command containing the current:

- controller URL
- agent secret
- node name
- WebSocket option
- work directory

Always use the command generated for the current node.

---

## 3. Prepare Ubuntu

Install Java:

```bash
java -version
sudo apt update
sudo apt install -y openjdk-17-jre
```

Create the agent directory:

```bash
sudo mkdir -p /home/rohit/agent
sudo chown -R rohit:rohit /home/rohit/agent
```

Switch to the Jenkins user:

```bash
sudo su - rohit
cd /home/rohit/agent
```

---

## 4. Download agent.jar

Use the URL generated by Jenkins:

```bash
curl -sO https://<jenkins-url>/jnlpJars/agent.jar
```

Verify:

```bash
ls -lh agent.jar
```

---

## 5. Run the agent manually

Typical command:

```bash
java -jar agent.jar \
  -url https://<jenkins-url>/ \
  -secret <AGENT_SECRET> \
  -name "ubuntu-agent-01-JNLP" \
  -webSocket \
  -workDir "/home/rohit/agent"
```

Run this on the **agent VM**.

A successful connection normally shows:

```text
WebSocket connection open
Connected
```

The node should become **Online**.

### Important

The following must belong to the current Jenkins node:

```text
-url
-secret
-name
```

The name must match the Jenkins node name exactly.

---

## 6. Run in the background

For a temporary lab test:

```bash
java -jar agent.jar \
  -url https://<jenkins-url>/ \
  -secret <AGENT_SECRET> \
  -name "<NODE_NAME>" \
  -webSocket \
  -workDir "/home/rohit/agent" \
  > agent.log 2>&1 &
```

Check:

```bash
ps -ef | grep '[a]gent.jar'
tail -f agent.log
```

Shell operators:

```text
&           run in background
> agent.log redirect stdout
2>&1        send stderr to the same log
```

You can also use:

```bash
nohup java -jar agent.jar ... > agent.log 2>&1 &
```

`nohup` protects the process from the terminal hangup signal.

For a persistent Jenkins agent, use systemd instead.

---

## 7. What is SIGHUP?

**SIGHUP** means **Signal Hang Up**.

It is commonly associated with the terminal or session that started a process going away.

Conceptually:

```text
SSH logout
   |
   v
Shell exits
   |
   v
SIGHUP may be sent
   |
   v
Background process may stop
```

`nohup` tells the process to ignore SIGHUP.

A process started with only `&` may also survive SSH logout depending on the shell/session configuration. This is why systemd is preferable for a service.

# 8. Run the inbound agent with systemd

For a persistent agent, systemd is the recommended approach.

## 8.1 Store the secret separately

Create:

```bash
sudo nano /etc/jenkins-agent.env
```

Put:

```text
JENKINS_SECRET=<CURRENT_AGENT_SECRET>
```

Protect it:

```bash
sudo chown root:root /etc/jenkins-agent.env
sudo chmod 600 /etc/jenkins-agent.env
```

### Is EnvironmentFile encrypted?

No.

`EnvironmentFile=` does not encrypt the secret. It keeps the value out of the main service file and lets systemd load it for the service.

For stronger secret protection, consider systemd credentials or a dedicated secrets manager.

---

## 8.2 Create the systemd service

Create:

```bash
sudo nano /etc/systemd/system/jenkins-agent.service
```

Example:

```ini
[Unit]
Description=Jenkins Inbound Agent
After=network-online.target
Wants=network-online.target

[Service]
User=jenkins
WorkingDirectory=/home/rohit/agent
EnvironmentFile=/etc/jenkins-agent.env

ExecStart=/usr/bin/java -jar /home/rohit/agent/agent.jar \
-url https://<jenkins-url>/ \
-secret ${JENKINS_SECRET} \
-name "<NODE_NAME>" \
-webSocket \
-workDir "/home/rohit/agent"

Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

Replace the URL and node name with the values from the current Jenkins node configuration.

Use the current node secret.

---

## 8.3 Start the service

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now jenkins-agent
```

Check:

```bash
sudo systemctl status jenkins-agent
```

Expected:

```text
Active: active (running)
```

Follow logs:

```bash
sudo journalctl -u jenkins-agent -f
```

Successful connection:

```text
WebSocket connection open
Connected
```

---

## 8.4 Useful systemd commands

```bash
sudo systemctl start jenkins-agent
sudo systemctl stop jenkins-agent
sudo systemctl restart jenkins-agent
sudo systemctl status jenkins-agent
sudo journalctl -u jenkins-agent -f
sudo journalctl -u jenkins-agent -n 50 --no-pager
systemctl is-enabled jenkins-agent
```

With `enable`, the agent service starts automatically after a VM reboot.

---

# 9. Why systemd is better

Manual process:

```text
SSH session
   |
   +-- java -jar agent.jar
```

systemd:

```text
Ubuntu VM
   |
   +-- systemd
         |
         +-- jenkins-agent.service
                |
                +-- agent.jar
```

systemd gives you:

- independence from SSH sessions
- automatic restart after failure
- automatic startup after reboot
- centralized logs through journald

---

# 10. Deleting a Jenkins node does not kill agent.jar

Deleting a node removes its Jenkins configuration. It does not automatically kill a Java process already running on the Linux VM.

You can have:

```text
Jenkins
  |
  X node deleted

Ubuntu VM
  |
  +-- agent.jar still running
```

If you recreate the node, the old process does not automatically discover the new node configuration.

Use the new command generated by Jenkins, especially the new **node name and secret**.

---

# 11. Avoid multiple agent.jar processes

Check:

```bash
ps -ef | grep '[a]gent.jar'
```

For one node, normally keep one intended agent process.

If you accidentally start multiple processes:

```bash
sudo kill <PID>
```

Then verify again:

```bash
ps -ef | grep '[a]gent.jar'
```

A systemd-managed process commonly has PPID 1 because systemd is its service manager.

# Troubleshooting

## 12. Handshake error

Typical log:

```text
WARNING: Did not receive X-Remoting-Capability header
INFO: Failed to connect: Handshake error.
INFO: Waiting 10 seconds before retry
```

The process is running, but the Remoting handshake is failing.

Check the following in order.

### A. Node name

Go to:

**Jenkins -> Nodes -> <node> -> Configure**

Compare the node **Name** with:

```text
-name "<NODE_NAME>"
```

They must match exactly.

For example:

```text
Jenkins node:
jenkins-agent-jnlp

Agent:
-name "jenkins-agent-jnlp"
```

Do not use an old name after recreating or renaming a node.

### B. Agent secret

Make sure the secret belongs to the **current node**.

If the node was deleted and recreated, use the newly generated secret.

### C. Controller URL

Check:

```text
-url https://<jenkins-url>/
```

It must point to the current Jenkins URL.

### D. Duplicate agent processes

Run:

```bash
ps -ef | grep '[a]gent.jar'
```

Stop stale manually started processes and let systemd manage the intended one.

---

## 13. `echo $JENKINS_SECRET` is empty

This is expected if the secret is loaded through:

```ini
EnvironmentFile=/etc/jenkins-agent.env
```

The variable is loaded into the **systemd service environment**, not your current interactive shell.

Therefore:

```bash
echo $JENKINS_SECRET
```

can be empty while the systemd service is correctly using the value.

Do not print the real secret into screenshots, logs, recordings, or documentation.

---

## 14. Agent survives SSH logout

A process started with:

```bash
java -jar agent.jar ... &
```

may survive logout depending on the shell/session.

You may see:

```text
jenkins  16847  1  ... java -jar agent.jar ...
```

The process has been re-parented to PID 1.

This does not replace systemd for a production-style service.

---

## 15. Agent goes Offline after Ctrl+C

If started in the foreground:

```bash
java -jar agent.jar ...
```

then pressing Ctrl+C terminates the Java process:

```text
Ctrl+C
   |
   v
agent.jar stops
   |
   v
Jenkins node goes Offline
```

This is expected.

---

## 16. systemd says active but Jenkins is Offline

A Linux service can be **active (running)** while the Jenkins WebSocket connection is failing.

Check:

```bash
sudo systemctl status jenkins-agent
sudo journalctl -u jenkins-agent -n 50 --no-pager
```

Good:

```text
WebSocket connection open
Connected
```

Problem:

```text
Handshake error
Did not receive X-Remoting-Capability header
Waiting 10 seconds before retry
```

If the Java process is running but the handshake fails, check the URL, node name, secret, and any reverse proxy or Cloudflare path.

---

## 17. Cloudflare Tunnel / reverse proxy

If Jenkins is exposed through Cloudflare or another reverse proxy, the WebSocket connection must work through that path.

Typical path:

```text
Ubuntu Agent
    |
    | HTTPS / WebSocket
    v
Cloudflare / Reverse Proxy
    |
    v
Tunnel
    |
    v
Jenkins Controller
```

From the agent, test the Jenkins URL:

```bash
curl -I https://<jenkins-url>/
```

Also inspect the Jenkins node log.

If the same inbound command previously connected successfully using `-webSocket`, that is useful evidence that the path can support WebSocket, but current node configuration and proxy settings should still be checked.

# 20. Final architecture

```text
                 Jenkins Controller
             https://<jenkins-url>/
                       ^
                       |
                 WebSocket / HTTPS
                       |
                       |
              Ubuntu Agent VM
                       |
                    systemd
                       |
             jenkins-agent.service
                       |
                   agent.jar
```

The key idea:

> **The inbound agent initiates the connection to the Jenkins controller.**

This is the main difference from **Launch agents via SSH**, where the controller initiates the SSH connection to the agent.
